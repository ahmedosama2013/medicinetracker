# Code review — September 2026

A full read of `js/`, `css/app.css`, `sw.js`, the migrations and the edge
functions, after Phase 2 shipped. Findings first, then the plan that falls out
of them.

> **All of these are fixed.** They became items `S1`-`S19` of
> [phase-2.5-plan.md](phase-2.5-plan.md), which also records what the plan got
> wrong and the two bugs the review itself missed. This document is kept as the
> diagnosis, not as an open list.

Severity is "what does the person holding the phone experience", not "how wrong
is the code".

---

## A. Races and correctness

### A1. Nothing serialises renders — this is the duplicated-slots bug

`router.renderRoute()` is `async` and has no generation guard. Every view
follows the same shape:

```js
clear(app);              // synchronous
const rows = await …;    // yields
app.appendChild(…);      // lands whenever it lands
```

Two overlapping renders therefore produce: A clears, A yields, B clears, B
yields, A appends its day, B appends its day. The result is **two full copies of
the day on screen, same slots, same medicines** — which disappear on reload
because the reload runs exactly one render. That is the symptom reported from
the phone.

There is no shortage of ways to overlap:

- `sync.startRealtime()` calls `refresh()` once per Postgres change event, and
  a Done tap on a five-medicine slot produces five `dose_log` events.
- Saving a medicine on the supporter side fires `medicines`, `schedules` and
  `slots` events, each of which calls `refetchRoutine().then(refresh)`.
- The supporter's 60s poll calls `router.refresh()` with no idea whether a
  render is already in flight.
- `calendar.js` calls `draw()` from `onClose`, from `step()` and from
  `pickMonth()`, none of which check the others.

**Fix:** a monotonically increasing render token in `router.js`. Bump it on
entry, and after every `await` a view is only allowed to touch the DOM if its
token is still current. Simplest version: serialise through a promise chain and
drop superseded renders entirely.

### A2. The elder's own writes re-render the screen underneath their thumb

`js/views/day.js` goes to real trouble to swap exactly one slot node on a dose
change, and explains why in a comment: re-rendering "re-reads the database,
reloads every photo and jumps the scroll position". Then `js/sync.js` subscribes
to `dose_log` and calls `refresh()` on every change — including the echo of the
write that was just made locally. The careful in-place update is immediately
followed by the full re-render it exists to avoid.

**Fix:** ignore realtime echoes of local writes (the outbox already knows the
row ids), and never full-refresh a screen for a change the screen already
applied. A2 and A1 compound: A2 is what generates the concurrent renders A1
turns into duplicates.

### A3. The routine cache is briefly empty during every refetch

`store.replaceMedicinesCache()` is `db.clear()` followed by `db.putMany()` — two
separate IndexedDB transactions. Any read landing between them sees zero
medicines. On the elder's Today that is not a blank list, it is the **cold-start
screen with their share code on it**, because `todayView` treats "no medicines"
as "nobody has set this up yet".

**Fix:** clear and write in one `readwrite` transaction. `db.js` needs a
`replaceAll(store, values)` for this; the current helpers each open their own.

### A4. `flushOutbox()` has no re-entrancy guard

Every `setDose` / `logSlot` / `undoSlot` calls `flushOutbox()` without awaiting
it. Tapping one medicine three times quickly starts three flushes that each read
the queue, then race to the network.

The outbox correctly stores one item per `dose:date:slot:medicine` key so the
*queue* holds only the final state. But two in-flight flushes hold two different
payload snapshots, and whichever HTTP request lands second wins. A fast
unmarked → taken → skipped ends with `taken` on the server while the phone says
`skipped`; realtime then pushes `taken` back and silently overwrites the
person's last tap.

**Fix:** a module-level `flushing` promise — if a flush is running, mark it
dirty and re-run once when it finishes.

### A5. The dose target accepts taps faster than it can process them

`cycleDose()` reads the current state from `stateByKey`, which is only updated
*after* the write resolves. A second tap arriving before then reads the stale
state and computes the same "next", so the tap is silently swallowed. The button
is never disabled and gives no in-flight feedback. The whole-slot Done button
does disable itself; the per-medicine one does not.

**Fix:** update `stateByKey` optimistically before awaiting and roll back on
failure, or ignore taps on a dose with a write in flight. Optimistic is better
here — it also removes the perceptible lag on a slow connection.

### A6. Nothing rolls the elder's Today over at midnight

`todayView` computes `const date = todayStr()` once, at mount. The elder's
device has no timer, no `visibilitychange` handler and no realtime event that
would fire at midnight. A phone left on the Today screen overnight — which is
the normal case for an installed PWA — shows **yesterday** in the morning, and
every dose marked goes to yesterday's `local_date`.

If the nightly freeze has advanced `locked_through` past that date, the write is
rejected by `dose_insert`, the outbox catch treats the rejection as "offline",
and it retries forever. The person sees a tick that never syncs.

The supporter is accidentally immune: their 60s poll calls `router.refresh()`,
which re-mounts the view and recomputes the date.

**Fix:** a visibility/focus handler plus a timer to the next local midnight, on
both roles. Related: the "Now" badge and `dayState()` in the calendar are
computed once per mount too.

### A7. No backfill after the realtime socket reconnects

`refetchHistory()` runs exactly once, at boot. Supabase's client reconnects the
websocket on its own, but events that happened while the phone was asleep are
never replayed. An elder whose phone slept all night will not see what the
supporter changed until the app is fully restarted — and `.subscribe()` is
called with no status callback, so a channel that fails to rejoin is invisible.

**Fix:** refetch on `SUBSCRIBED` and on `visibilitychange`, and surface a
"last updated" line the way the supporter's Today already does.

### A8. Closing a calendar day sheet early leaks its photos

```js
let rendered;
const sheet = openSheet({ …, onClose: () => { rendered?.cleanup(); … } });
rendered = await renderDay({ … });
sheet.setContent(rendered.node);
```

Close the sheet during that `await` — easy, the sheet is on screen showing
"Loading" — and `rendered` is still `undefined`, so `cleanup()` never runs and
every object URL for that day leaks. `setContent` then writes into a detached
node. Tapping two days quickly opens two sheets.

**Fix:** track whether the sheet is still open and clean up unconditionally when
the render finishes late.

### A9. Overlapping renders lose the previous view's cleanup

`renderRoute` keeps one `activeCleanup`. If render B starts before A has
returned, B sees `activeCleanup === null` (A hasn't assigned it yet), A assigns
it, B overwrites it — and A's photo object URLs are never revoked. Fixed for
free by A1.

## B. "Is it doing anything?" — feedback gaps

### B1. Saving a medicine has no feedback and can save twice

`medicine-form.js`'s Save button is never disabled and shows no spinner. The
handler does up to three sequential round trips (`upsert_medicine`,
`replace_schedules`, then a photo upload through an edge function that can cold
start). On a Pakistani mobile connection that is comfortably two or three
seconds of a button that looks untouched.

Two taps in that window run `save()` twice with `draft.id` still `null` on the
second one — **two medicines, same name, both on Today**. This is the same class
of bug as the medicine list one already fixed, on the screen where it costs the
most.

**Fix:** disable + spinner for the duration, and an `if (saving) return` guard.

### B2. `slotsView` has neither a loading state nor error handling

```js
const routine = await supporter.loadRoutine(code);   // no try/catch, no spinner
```

The previous screen stays on screen for the whole round trip, and if the call
fails the view function rejects — `renderRoute` doesn't catch, so the person is
left on the old screen with a console error and no explanation. Every other
supporter screen got a `loadingState()` in Phase 2; this one was missed.

Saving a slot time or label has no feedback either: `persist()` is awaited and
then `draw()` redraws, with nothing in between.

### B3. Elder Settings can hang on `serviceWorker.ready`

`settingsView` clears the screen, appends the title, then awaits
`auth.getSession()` and `pushLib.isSubscribed()`. `isSubscribed()` awaits
`navigator.serviceWorker.ready`, **which never resolves if no worker ever
activates** — a failed `sw.js` fetch, a hard-reloaded tab. The screen stays as a
lone "Settings" heading indefinitely, and there is no timeout.

**Fix:** a loading state, and a timeout on `serviceWorker.ready`.

### B4. `toggleNotifications` has no busy state

It awaits a permission prompt, a browser subscribe and a database upsert with
the button live the whole time.

### B5. A supporter's own save doesn't reach their own Today

`medicine-form.js` writes through `supporter.js` and navigates to
`#/medicines` — which reads live, so the list is right. But **Today** and the
list's *photos* read the local cache filled by `supporter-sync.js`, and nothing
invalidates it on save. A medicine added on the supporter's phone does not
appear on their own Today, and its freshly uploaded photo shows the fallback
tile, for up to 60 seconds.

**Fix:** `await supporterSync.refresh(code)` after a successful save.

### B6. The medicine form re-renders itself completely on every change

`draw()` does `clear(app)` and rebuilds the entire form. It is called when the
slot select changes, the frequency select changes, a weekday chip is toggled, a
schedule is added or removed, and after a photo is picked. Field values survive
(they live in `draft`), but focus does not, the scroll position of a long form
jumps, and it reads as the page reloading — which is exactly the complaint.

**Fix:** rebuild only the schedule card that changed. The form already has the
right seam (`scheduleCard(entry, index)`); it just needs the same
`replaceWith` treatment `day.js` gives a slot.

### B7. Toggling "Show archived" refetches the whole routine

`showArchived = !showArchived; refresh()` re-runs `medicinesView`, which calls
`loadRoutine()` over the network to flip a local boolean.

## C. Wrong answers and silent failures

### C1. A nudge that reached nobody says "Reminder sent"

The edge function is careful to distinguish outcomes and returns
`{ sent: 0, reason: 'send-failed', detail: [...] }` when every push fails. The
client checks `retryInMinutes` and `no-subscriptions`, and falls through to
`toast(S.nudgeSent)` for everything else — including that one. The supporter is
told the nudge landed when it did not, which is precisely the failure this
feature exists to remove.

**Fix:** treat `sent === 0` as not-sent and say so.

### C2. `push.unsubscribe()` discards its delete error

```js
await supabase().from('push_subscriptions').delete().eq('endpoint', sub.endpoint);
await sub.unsubscribe();
```

If the delete fails the browser still unsubscribes, so the UI reports reminders
off while the server row survives and the cron job keeps pushing to a dead
endpoint. This is the mirror image of the bug already fixed in `subscribe()`,
and it is the same discarded-`error` pattern that has now caused four separate
silent failures in this codebase.

### C3. Signing out leaves the previous household's data on the device

`signOut()` writes `{ role: null, householdId: null, shareCode: null }` and
reloads. `disconnect()` does the same for the supporter. Neither clears
`medicines`, `schedules`, `doseLog`, `daySnapshots` or `photos`.

`replaceMedicinesCache` will overwrite medicines on the next sync, but
`doseLog`, `daySnapshots` and `photos` are only ever *added* to. Sign in as a
different account, or pair to a different household, and the previous
household's dose history and pill photos are still in IndexedDB and still render
on the calendar. That is a privacy problem, not just a staleness one.

**Fix:** wipe every store except `settings` on sign-out and on disconnect.

## D. Styling and accessibility

The design system itself is in good shape — tokens are consistent, dark mode is
a real second palette rather than an inversion, `prefers-reduced-motion` is
honoured, `:focus-visible` is styled, safe-area insets are handled, and every
icon name used in `js/` exists in the CSS. The gaps are behavioural:

- **No focus trap in overlays.** `mountOverlay` sets `aria-modal="true"` and
  focuses the first control, but Tab walks straight out into the page behind,
  and focus is not restored to the trigger on close. On the photo viewer and the
  medicine sheet this is the difference between usable and not for keyboard and
  switch users.
- **`toast()` hide-timer race.** `hide()` schedules `node.hidden = true` 250ms
  out. A toast raised inside that window is made visible and then hidden by the
  previous toast's timer. Reachable by cycling two doses quickly.
- **The paper grain is a fixed, full-viewport layer** and in dark mode it also
  carries `mix-blend-mode: screen`. Worth measuring scroll performance on the
  oldest phone this has to run on before it ships wider.
- **`#app` carries a `fade-in` animation** that only ever plays once, since the
  node is reused across renders. Harmless, but it means the intended transition
  between screens does not actually happen.

## E. Docs and repo hygiene

- **`custom.txt` holds a live Google OAuth client secret** in the working tree.
  It is untracked and does not appear anywhere in history — verified — and
  `.gitignore` covers it. But it sits next to files that do get committed, and
  one `git add -f` or one careless edit to `.gitignore` leaks it. Move it out of
  the repository directory entirely.
- **`.gitignore` still lists `js/config.js`**, which is now tracked. Git keeps
  tracking it so nothing breaks, but the line now says the opposite of what the
  repo does, and `docs/setup.md` tells people to edit that file.
- **`docs/repo-structure.md` stops its migration list at `0007`.** `0008`
  (nudge grants), `0009` (reminder RPC wrappers) and `0010` (slot time in
  snapshots) are missing — and `0009` in particular is the one someone setting
  up a fresh project will not think to look for.
- Everything else reads as current. `architecture.md`, `flow.md`, `ui.md` and
  `setup.md` all match the code, including the deliberate reversals
  (supporter cache, dose_log UPDATE policy) which are documented with their
  reasoning intact.

# Plan

The stability work these findings imply is planned in full in
[phase-2.5-plan.md](phase-2.5-plan.md), as items `S1`-`S19` with an order of
work and a verification list. Every finding above maps to one of them.

What follows is only how the rest of the roadmap is affected.

## Phase 3 — Organiser mode

Unchanged from `v3-plan.md` (items 18–22), with **item 23 pulled forward first**
— purpose line and packet photo. The plan already flags that building the step
screen before item 23 means building it twice.

Still to settle inside the phase: compartments per day versus slots, half
tablets, an explicit "nothing today" for non-daily schedules, numerals for doses
above one, and keeping syrups/drops/inhalers out of the box.

Two things from this review feed straight into it:

- The wake lock (item 21) needs the visibility handling from S6/S7 anyway.
- "I don't have enough" (item 22) writes from the *supporter's* device to the
  *elder's* Today, which is a new write path — it should go through
  `js/doses.js`'s role seam rather than growing a second one.

## Phase 4 — Roadmap

As planned: item 24 (supporter push identity) unblocks 25 and 26 and they land
together; then 27 (DRAP autocomplete, which rebuilds the medicine form
search-first), 28 (crowdsourced photos), 29 (verify push on a real iOS
home-screen install).

Item 29 is worth doing early and out of order — it is a test, not a build, and
everything about reminders is currently believed rather than observed on the
device that matters.

## Still unaddressed from earlier phases

- `db.js`'s `upgrade()` is version-agnostic and cannot add an index to an
  existing store. Nothing needs one yet. The first feature that does will need a
  real migration path written first.
- Guided photo capture — a preview at the tile's real size, so a photo is
  framed for where it will actually be seen. The `object-fit: contain` fix made
  wide photos legible; it did not make them well-framed.
